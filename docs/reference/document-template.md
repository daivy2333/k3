# 主题文档模板

> 适用范围: `docs/` 下所有主题文档的写作约束与可复用骨架。
> 产品文档通过获批 OpenSpec change 修改；change accepted 后，docs-maintainer 仅按实际结果同步 SNAPSHOT、tasks、M/D/K/R/I 中适用的状态。
> 写作约束来源: M01（单一权威源）、M02（输出形态与目录边界）、M03（语言与术语）、M04（无可执行代码）、D01（纯 Markdown 聚合）、D02（主题驱动目录）。

## 命名与目录

- 路径: 全部位于 `docs/` 顶层或子目录；禁止在仓库其它位置新建内容文件。
- 文件名: kebab-case；反映主题，不复制源页面 slug。
- 目录划分: 按主题，不镜像官网 URL 树（D02）。
- 单文件建议: ≤ 500 行；超过时按主题拆分为同目录子文件，并保留目录索引。

## 首行来源格式

每个文档第一行必须使用引用式段落表达来源、源端修订和观察日期。

### 单来源

```markdown
> 来源: <URL>（源端修订: YYYY-MM-DD 或 unknown；观察日期: YYYY-MM-DD）
```

- `URL` 必须是当前覆盖表登记的 URL。
- 源端修订未知时写 `unknown`；不能用观察日期冒充源端修订。
- 观察日期使用 YYYY-MM-DD；本 change 初始 baseline 为 `2026-09-02`。

### 多来源

```markdown
> 来源: <URL_A>（源端修订: ...; 观察日期: ...）; <URL_B>（源端修订: ...; 观察日期: ...）; <URL_C>（源端修订: ...; 观察日期: ...）
```

- 多个直接来源以分号 `;` 分隔，写在同一行。
- 正文需在每项事实下注明该条所属来源；不得在正文中省略归属。
- 当来源超过三个时，优先合并为「主来源 + 交叉验证」两组，避免首行过长。

### 源端修订与观察日期的区别

- 源端修订: 页面或文档系统给出的修订日期；缺失时必须写 `unknown`。
- 观察日期: 本仓库维护者在本次整理时观察该页面的日期；变更必须新建 refresh change 并改写。
- 两个日期不可合并、不可互相替代。

## 标题与目录

- 标题层级: `#` 用于文档主标题；`##` 用于主题分节；`##` 之下使用 `###`；禁止跨级跳号。
- 标题层: 使用术语表登记的主写法；不出现中英混排的同义并列。
- 目录: 当 `##` 数量 ≥ 3 时，在文件顶部紧跟首行后插入目录列表，使用相对锚链接。

## 证据强度（必须标注）

每条事实必须在行内或紧随段落标明证据强度，证据强度为以下四级之一：

| 标记 | 含义 | 来源要求 |
| --- | --- | --- |
| `官方事实` | 官网正文直接陈述 | R01 入口及其下级页面 |
| `交叉验证` | 由官方 GitHub、DTS 或驱动行为佐证 | R08 类仓库或 DTS 文件 |
| `推论` | 由多个事实推出但源页面未直接陈述 | 必须列出所依据的多项事实 |
| `未知项` | 当前证据不足 | 必须列出解除条件 |

混用场景：同一段落含多类证据时，按事实逐条标注，不写整段统一强度。

## 未知项表达

当资料不足时使用 `未知项:` 段落，并至少包含以下字段：

- 当前证据: 已收集到的、但不足以得出结论的线索。
- 禁止推断: 明确不得用相邻章节或外部资料替代证据的内容。
- 解除条件: 哪些信息出现后可转为 `官方事实` 或 `交叉验证`。
- 影响主题: 哪些后续主题文档依赖该缺口解除。

## 拆分规则（> 500 行）

- 触发: 接近或超过 500 行时（建议阈值 450 行留余量）。
- 拆分方式: 按主题子域拆分为同目录子文件，主文档保留目录与导航。
- 拆分后: 每篇子文件保留独立首行来源；多来源文档的子文件复用主文档来源。
- 索引更新: 在 `docs/index.md` 或目录 overview 中增加子文档链接。

## 反例

以下写法不符合本模板，禁止使用：

- 仅有标题与正文，缺少首行 `> 来源:`。
- 源端修订处写 `观察日期` 或反之。
- 把 GitHub issue 或博客当作 `官方事实`。
- 在标题层并列同义术语，如「CoM260 Kit / 套件」。
- 把推论或交叉验证直接写为「官方事实」。
- 在多来源首行只写一个 URL、其余来源放到正文而不参与首行。

## 模板：最小可复制骨架

### 单来源骨架

```markdown
> 来源: <URL>（源端修订: <YYYY-MM-DD 或 unknown>；观察日期: <YYYY-MM-DD>）

# <主题>

> 一句话点明本主题在 K3 CoM260 文档体系中的职责与边界。

## <子主题 1>

- 事实: ...（官方事实）
- 事实: ...（交叉验证；依据: <Rxx 或 R08 子仓库>）

## <子主题 2>

- 事实: ...（官方事实）

## 未知项

- 当前证据: ...
- 禁止推断: ...
- 解除条件: ...
- 影响主题: ...
```

### 多来源骨架

```markdown
> 来源: <URL_A>（源端修订: ...；观察日期: ...）; <URL_B>（源端修订: ...；观察日期: ...）

# <主题>

> 一句话点明本主题在 K3 CoM260 文档体系中的职责与边界。

## <子主题 1>

- 事实: ...（官方事实；来源: <URL_A>）
- 事实: ...（交叉验证；来源: <URL_B>）

## 未知项

- 当前证据: ...
- 解除条件: ...
- 影响主题: ...
```

## 与覆盖表的关系

- 任何出现在首行或正文引用的 URL 必须先在 [`source-coverage.md`](source-coverage.md) 登记。
- 状态变更（active / deferred / out-of-scope / supporting）需先在覆盖表登记，再在主题文档中引用。
- 主题文档不复制覆盖表的字段；仅以相对链接引用。
